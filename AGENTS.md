# Project Rules

- Before changing code, read `README.md` (especially "安装、更新与卸载") and the latest entry in `ACCEPTANCE.md`. Read `INSTALL.md` for installation changes and `docs/development.md` for development and release checklists.
- Treat each distributed UI change as a new plugin release: bump the version in `package.json`, `package-lock.json`, `.codex-plugin/plugin.json`, `.claude-plugin/marketplace.json`, and `src/shared/security.ts`. Keep `UI_URI` derived from `VERSION`; never reuse a published UI resource URI for changed HTML, CSS, or JavaScript.
- Before distributing, run `npm run check` and `npm run release:package`. CI must not download Codex CLI or run CLI installation/update/rollback tests; keep `npm run test:package` as an optional local check using an existing CLI. Follow the release checklist in `docs/development.md` and verify the opened UI in a new Codex conversation; build/manifest/CLI checks alone do not prove the host displays the new page.
- Distribute `dist/marketplace` from a stable path under each user's own `CODEX_HOME`. Use official `codex plugin` commands; do not edit Codex-managed plugin caches or users' credentials, connection configuration, or model catalogs.
- Record release verification and any host-only limitations in `ACCEPTANCE.md` without claiming native UI validation from isolated tests.
- Use Shanghai release-minute versions: display, tags, and ZIP names use `vYYYY.MMDD.HHmm`, padding both MMDD and HHmm to four digits (including midnight `0000`). Package manifests and protocol VERSION use numeric SemVer components without leading zeros or `v`; derive display versions through the shared releaseTag helper. Run `npm run version:release`; never reuse a published version.
- Ship versioned ZIP/SHA256 release assets with INSTALL.md and checked native launch configuration. Prefer the client-provided Node >=24; never assume a system Node or POSIX shell on Windows, install a runtime silently, or claim Windows validation from macOS tests.
- Installer changes must cover name/root-only CLI metadata, add-first version updates, verified same-version no-ops, rollback and cleanup warnings. Run Windows native isolated installation QA with a live old backend and a real deny-delete file handle when available; never hand-edit managed caches, kill user processes, or treat a cleanup warning as installation failure.
- Use English for commit messages, PR titles, and release titles. Keep `README.md` in Simplified Chinese as the default and maintain `README.en.md` as its English counterpart, with language links in both files. Include both READMEs in plugin builds and release archives.
- Use only the canonical GitHub remote for development and releases. Default to one feature/version PR and one protected-main release workflow: review versions in the same PR, build once after merge, approve the protected release environment, and serialize publishing. Stage a draft GitHub Release at the exact source SHA, upload ZIP/SHA256, verify downloads, then publish. Do not trigger tag workflows. Keep stable README links; Release records SHA256, source and workflow, so no post-release status-only PR is required. Never overwrite published bytes, reuse versions, distribute from Git asset branches, or claim Actions is active before a real job passes. Main protection and release-environment approval must be configured before a publishing merge.
